# 外部サービスとの連携

GitHub に加えて、GitLab・Linear・Jira・Slack とつなげられます。GitHub の使い方は、これまでと変わりません（`gh` を使い、トークンの設定は要りません）。

## できること

| | GitHub | GitLab | Linear | Jira |
| --- | --- | --- | --- | --- |
| タスクの元にする入力 | `12`、`12, 15, 18` | `12`、`#12`、`group/project#12`、Issue の URL | `ENG-123`、Issue の URL | `ABC-123`、課題の URL |
| PR / MR の本文に入る1行 | `Closes #12` | `Closes #12` | `Ref ENG-123 <URL>` | `ABC-123 <URL>` |
| 状態の同期で変えるもの | GitHub Projects の Status | ラベルと、Issue の開閉 | ワークフローの状態 | トランジション |
| コメントの書き戻し | なし | あり | あり | あり |
| サブIssue | サブIssue | 子タスク（使えない版では関連 Issue） | サブIssue | サブタスク |
| PR / MR の作成と確認 | `gh` で行う | GitLab の API で行う | リポジトリのホストに任せる | リポジトリのホストに任せる |

Linear と Jira が扱うのは課題だけです。PR / MR は、リポジトリのホスト（GitHub なら `gh`、GitLab なら API）で作るか、直接マージします。

Slack は課題管理サービスではありません。通知の投稿、Slack からのタスクの開始、承認と回答に使います（[下](#slack)）。

すべてのサービスに共通の動きです。

- **指示**: Issue のタイトル・本文・ラベルと、新しいコメント 20 件までから、エージェントへの指示を作ります。1 Issue が 1 枚のカードになります
- **状態の同期**: カードが実行中・待機中のときは進行中、レビュー・エラーのときはレビュー、マージして完了するか手で完了にしたときは完了にします。PR / MR を作っただけなら、マージされたのを見つけるまでレビューのままです
- **コメント**: タスクの開始・PR / MR の作成・完了のときに、Issue にコメントを書きます。「Issue 連携」の「タスクの開始・PR の作成・完了を Issue にコメントする」で切れます
- **サブIssue**: Issue から作るとき、開いているサブIssue をそれぞれサブタスクにします。エージェントのサブタスクの提案を受けるときは、確認のうえで、サービスにもサブIssue を作れます
- **失敗したとき**: 状態の同期やコメントに失敗しても、タスクは止まりません。理由はカードのログに出ます

## 設定のしかた

1. 「設定」→「連携」で、サービスの接続先とトークンを入れて「保存」を押します。「接続テスト」で確かめられます
2. 課題管理サービスを使うプロジェクトでは、「このプロジェクト」→「Issue 連携」の「使う課題管理サービス」で選びます。プロジェクトごとに1つ選びます
3. 「＋ 新しいタスク」の Issue のタブに、番号や URL を入れます。タブには選んだサービスの名前が出ます

「連携」の項目は、どのプロジェクトでも同じです。「Issue 連携」の項目は、プロジェクトごとです。

初めて開くリポジトリの origin が、連携を保存した GitLab のものなら、GitLab を選んだ状態で始まります。リポジトリを先に開いていたときは、手で選びます。「レビュー後の取り込み方」も、そのときに「直接マージする」になっていれば「MR を作成する」に変えます。

## GitLab

gitlab.com とセルフホストの GitLab に対応しています。`glab` は使いません。

| 項目 | 説明 |
| --- | --- |
| 接続先の URL | 初期値は `https://gitlab.com`。セルフホストではそのサーバーの URL を入れます。サブパス（`https://example.com/gitlab`）でも動きます |
| http の接続先を許可する | `http://` の接続先を使うときだけチェックします。トークンが暗号化されずに流れます |
| Personal Access Token | `api` のスコープを付けて作ります |

- **MR**: origin が接続先の GitLab のものなら、そのリポジトリは `gh` の代わりに GitLab の API を使います。レビュー中のカードのボタンが「MR を作成」になります。同じブランチの MR が開いていれば、新しく作らずにそれを使います
- **MR の確認**: マージされたこと、コンフリクト、パイプラインの結果を確かめます。マージを見つけると、タスクを完了にします。MR のマージそのものは GitLab で行います
- **状態の同期**: 列に合わせてラベルを付け替えます。名前は `In progress` / `In review` / `Done` で、「Issue 連携」で列ごとに変えられます（1つだけ。複数書くと最初の名前を使います）。ラベルが無ければ GitLab が作ります。完了で Issue を閉じ、動き出したら開き直します
- **サブIssue**: 使える版では子タスク（Work Items）にします。使えない版や、親が子を持てない種類のときは、Issue を作って関連づけます
- **別のプロジェクトの Issue**: `group/project#12` か URL で指定できます。origin のプロジェクトの Issue は、番号だけで指定できます

## Linear

接続先は `api.linear.app` で固定です。

| 項目 | 説明 |
| --- | --- |
| API キー | Linear の Settings の Security & access にある Personal API keys で作ります。Issue の読み書きとコメントの権限が必要です |

- **状態の同期**: Issue のチームのワークフローから選びます。実行中は `started` の型の状態、レビューは In Review などの `started` の状態、完了は `completed` の型の状態です。レビューに当たる状態がなければ、開始済みのままです
- **名前の指定**: 「Issue 連携」で、列ごとに使う状態の名前を指定できます。指定した列は、その名前の状態だけを使います
- **PR の本文**: `Ref` で書くので、PR のマージで Linear 側が Issue を閉じることはありません。閉じるのは状態の同期です

## Jira

Jira Cloud と Jira Data Center に対応しています。

| 項目 | 説明 |
| --- | --- |
| Jira の種類 | Jira Cloud か Jira Data Center |
| Jira の接続先 URL | `https://example.atlassian.net` など。コンテキストパスがあるときは含めます（`https://jira.example.com/jira`） |
| Jira への http の接続を許可する | `http://` の接続先を使うときだけチェックします。トークンが暗号化されずに流れます |
| メールアドレス | Atlassian のメールアドレス。Cloud でだけ使います |
| トークン | Cloud は API トークン、Data Center は Personal Access Token |

- **URL**: 接続先と違うサイトの URL は受け付けません
- **状態の同期**: その課題で今使えるトランジションから選びます。実行中と完了は状態カテゴリ（In Progress / Done）で選び、レビューは名前に Review を含むものだけを選びます。当てはまるものがないときや、Jira が断ったとき（必須の項目があるなど）は、状態を変えずに理由をログに出します
- **名前の指定**: 「Issue 連携」で、列ごとにトランジションか移動先の状態の名前を指定できます（カンマ区切りで候補を複数書けます）
- **サブタスク**: プロジェクトにサブタスク用の課題タイプが必要です。サブタスクの下にサブタスクは作れません

## Slack

通知の投稿、Slack からのタスクの開始、通知のボタンでの承認と回答に使います。受信には Socket Mode を使うので、公開サーバーもポートの開放も要りません。**動くのはアプリを開いている間だけです。** 閉じている間は、どれも動きません。

Slack アプリの作り方は、「連携」の Slack の欄の「設定のしかた」にも出ます。

1. <https://api.slack.com/apps> で Slack アプリを作ります
2. 「Socket Mode」を有効にして、App-Level Token（スコープは `connections:write`）を作ります
3. 「OAuth & Permissions」の Bot Token Scopes に `app_mentions:read` と `chat:write` を足します。/コマンドも使うなら `commands` も足します
4. 「Event Subscriptions」を有効にして、Bot Events に `app_mention` を足します。/コマンドを使うなら「Slash Commands」で作ります（Request URL は要りません）
5. 通知のボタンで承認と回答をするなら「Interactivity & Shortcuts」を有効にします（Request URL は要りません）
6. ワークスペースにインストールして、使うチャンネルに Bot を招待します

| 項目 | 説明 |
| --- | --- |
| Bot Token | `xoxb-` で始まるトークン |
| App-Level Token | `xapp-` で始まるトークン |
| 通知を投稿するチャンネル ID | `C0123456789` の形。空なら投稿しません |
| 完了・失敗・確認待ちを通知する | 種類ごとに切れます（初期値はすべてオン） |
| タスクの開始と承認・回答ができる Slack ユーザー ID | `U0123456789, U0987654321` の形。**空なら誰も開始も承認もできません** |
| チャンネルとプロジェクトの対応 | 1行に `C0123456789 /path/to/project` の形で書きます。書いたチャンネルからだけ開始できます |

- **通知の種類**: 失敗には、スケジュールの失敗も入ります。確認待ちは、仕様の確認・権限の確認・質問・回答待ち・レビュー待ち・コンフリクトです
- **タスクの開始**: 対応を書いたチャンネルで、Bot へのメンションか /コマンドに指示を書きます。許可した人の依頼だけを受け付け、それ以外には断りの返事をします
- **開始したあと**: ふつうのタスクと同じで、内容が詰まっていなければ仕様の確認で止まります。権限の設定はプロジェクトのものを使います
- **知らせ**: Slack から頼んだタスクの知らせは、通知の種類の設定によらず、そのスレッドに投稿します
- **承認**: 権限の確認の通知に、ツールの入力と「許可」「拒否」のボタンが付きます。入力が長くて全文を出せないときは、「拒否」だけが出ます。「常に許可」はアプリの画面で行います
- **回答**: エージェントの質問・仕様の確認・回答待ちの通知に「回答する」ボタンが付き、押すと開く画面で答えられます。答えていない仕様の質問は「おまかせ」として送ります
- **ボタンを押せる人**: 上の一覧にある人だけです。それ以外の人には、本人にだけ見える断りの返事をします。一覧が空か、App-Level Token がないときは、ボタンを出しません
- **答えたあと**: Slack とアプリのどちらで答えても、通知からボタンが消えて、結果と答えた人が残ります。カードのログにも残ります。アプリを再起動すると、前の通知のボタンは使えません。そのときはアプリの画面で答えます
- **投稿の内容**: 権限の確認の通知には、ツールの入力が 4000 文字まで入ります。チャンネルの人に見えるので、ボタンを使うときは、見せてよい人だけのチャンネルにしてください
- **できないこと**: マージとレビューは、Slack からはできません。アプリの画面で行います。指示にするのは呼びかけたメッセージの本文だけで、スレッドの中身や添付ファイルは読みません。ダイレクトメッセージからは開始できません

## トークンと接続

- トークンは OS の安全な保存先の鍵で暗号化して、`board.json` とは別のファイルに保存します。平文では保存しません。Linux では GNOME Keyring や KWallet などが必要で、使えなければトークンを保存できません
- 保存したトークンは画面に出ません。エージェントにも渡しません
- 接続先の URL を変えると、一緒に入れ直さなかったトークンは消えます。別の接続先へ送らないためです
- 別の PC からボードを操作しているときの「連携」は、ホストの設定です。クライアントからトークンを入れ直せますが、保存したトークンの値は受け取れません
- 「削除」で、そのサービスの接続先とトークンを消します

## できないこと

- OAuth のログインはありません。トークンを入れて使います
- サービス側の変更はカードに戻りません。Linear や Jira で状態を変えても、カードの列は動きません
- タスクを作ったあとで Issue に書かれたコメントは、エージェントに届きません
- 1つのプロジェクトで使える課題管理サービスは1つです
